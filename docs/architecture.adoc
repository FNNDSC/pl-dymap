= pl-dymap: architecture
:toc:

== Abstract

pl-dymap is six modules: `models` holds every value that is not a primitive and crosses a function boundary, the flags, the job's environment, the plan, CUBE's answers and the run record among them, each a dataclass; `plan` computes the plan from the input and the flags without CUBE; `cube` is a typed client for the CUBE calls a plan needs, standard library only; `post` checks the plan against CUBE and creates one child per item at most once, a plugin instance or a pipeline workflow; `dymap` is the run, writing the plan before posting and the record after; `__main__` holds the parser, the manual and the decorated main. It depends on chris_plugin, pftree for its filter grammar and manual renderer, and pflog for the run's span.

== The plan

The body turns chris_plugin's namespace into an `Options` record at once and reads the job's environment into a `JobEnv`, whose token is kept out of its `repr`. `items_find` walks the input with `os.walk`, following symbolic links, since a pl-dircopy node presents its data through one, and visiting each real directory once, so a link that points back up cannot loop; hidden directories are neither items nor walked into, and the input itself is never an item, since no directory filter a child is given can select it. A directory is an item when it passes the three conditions of the `ItemSelection`: it is at `--itemDepth` below the input; its relative path passes `--itemDirFilter`, in pftree's grammar against the same relative paths the receiving plugin's own `--dirFilter` uses; and, when `--itemFileFilter` is set, it holds directly a file whose name passes that filter, through pftree's own file-name filter. `--itemDepth` 0, the default, means any depth when a file filter is set and the input's own subdirectories when not, so that 1.0.0's behaviour is what a run with no item flags gets. `params_parse` reads `--params` into `ParamSetting` records, by piping title and parameter for a pipeline and by parameter alone for a plugin, and refuses values that are not strings, numbers or booleans. `plan_build` refuses a plan with no items, more than `--maxItems`, or an item whose value would contain the comma that separates filter tokens. Each item's title is the shortest end of its path that no other item's title shares, its final name when that is unique, as much of its path as tells it apart when names repeat, `sub-01/MPRAGE` beside `sub-02/MPRAGE`; the titles depend on the whole set of items, which a data node's fixed output keeps the same from run to run, and are cut from the front to CUBE's hundred characters. Its value is `--itemTemplate` with `{item}` replaced by its path and `{itemRegex}` by the path escaped for a regular expression, the default `re:^{itemRegex}$` matching that one directory, so that `sub-01` does not also select `sub-010`. The plan records the plugin or the pipeline, the receiving piping and parameter, the further settings, the data node's id from `CHRIS_PREV_PLG_INST_ID`, and the items; it is written as `plan.json` before anything else happens.

== Posting

`target_resolve` resolves what the plan names. For a plugin, given as `name` or `name@version`, it lists the plugin's versions through CUBE's `name_exact` search and takes the one named or else the newest, and checks the receiving parameter and every `--params` entry against the plugin's parameters. For a pipeline it finds the pipeline by exact name, its pipings, and its parameters; the receiving piping is the one titled `--itemPiping`, or the pipeline's only piping, and the receiving parameter and every `--params` entry must exist on their pipings. A plan that does not fit is rejected and nothing is created. For each item `existing_find` lists the data node's children with the item's title, through the instance search's `previous_id` and `title` filters, matching the title exactly since CUBE's title filter matches substrings, and accepts a child only if it runs the same plugin, by id and so by version, on its own rather than inside a workflow, or belongs to a workflow of the same pipeline; a child CUBE cancelled or that finished with an error is not accepted, nor a workflow any of whose instances was, so a rerun makes the item again, while a child still running is accepted, since it may yet succeed. A found item is recorded as skipped with its instances and workflow. Otherwise, for a plugin, `instance_post` creates an instance under the data node titled by the item, with the `--params` values and the item's value; for a pipeline, `workflow_post` creates a workflow with `previous_plugin_inst_id` set to the data node, a title of the pipeline's name and the item, and `nodes_info`, built as `NodeInfo` records, giving the receiving piping the item's title and value and the `--params` pipings their values, the rest taking the pipeline's defaults. A CUBE error on one item is recorded and the run continues.

== The client

`CubeClient` sends `Accept: application/json`, which CUBE answers with paginated `count`, `next` and `results`, and follows `next` to the end. Every answer is decoded into a `JsonRow`, whose typed reads turn it into a record before it leaves the module, and every request body is a `JsonRow` built from records, so no other module touches CUBE's JSON. The token is held in a private attribute, sent only as the `Authorization` header, and kept out of `repr`, records and messages. HTTP errors become `CubeError` with the status and the first five hundred characters of CUBE's answer; an unreachable CUBE is status 0. The posting step takes any object with the client's methods, the `CubeApi` protocol, so the tests drive it with a stand-in.

== The run and its records

`dymap_run` checks the flags, exactly one of `--plugin` and `--pipeline`, no `--itemPiping` with a plugin, sane limits, builds and writes the plan, and on `--dryRun` writes a record of planned items and stops, needing no CUBE. Otherwise it takes the URL from `--CUBEurl` or `CHRIS_URL` and the token from `CHRIS_USER_TOKEN`, posts, and writes `created.json`: the CUBE URL, the data node, the plugin's id or the pipeline's and piping's, one outcome per item with its instances and workflow, the counts, the overall status and any error that stopped the run. A refused plan, a rejected plan, a missing token and an unreachable CUBE each leave a `created.json` that says so. The exit status is 0 when every item was posted or skipped, 1 when anything failed or the run could not proceed, 2 on a usage error; `@timed` writes the span on standard error with that status.

== The image and the workflow

The image is `python:3.12-slim` with the package installed; the plugin runs no programs, so it needs nothing else, and asks ChRIS for 100Mi and half a core. The CI workflow is the stack's template: lint and test on Python 3.11 to 3.14, build the image on a push to `main`, and on a `v*` tag check the tag against `__version__`, push to Docker Hub and ghcr.io, and upload the description to cube.chrisproject.org.

== Verification

Twenty-nine tests and the modules' doctests, eighty-three in all. The plan finds items at depth one and two, at any depth under a file filter, with the directory and file filters combined, through a symbolic link once and past a link back up, titles items by their shortest unique path end, series named alike under several subjects included, within CUBE's length limit, and refuses too many items, commas, a template without the item and a selection with no items. Against a stand-in CUBE a pipeline run creates one workflow per item under the data node with the exact node information, a rerun skips what exists and creates only a new item, a child of the same title from another pipeline is not taken as ours, a failure on one item leaves the others created and exits 1, a misspelt item parameter or `--params` entry is rejected before anything is created, and an unknown pipeline, missing environment and malformed or conflicting flags give 1 or 2. A rerun makes again an item whose child was cancelled or finished with an error, or whose workflow holds such an instance, and skips one still running. A plugin run creates one instance per item with the `--params` values and the item's value, takes the newest version unless one is named, skips on a rerun, treats an instance of another version, or one inside a workflow, as not ours, and rejects an unknown plugin or version, a misspelt item parameter and an unknown `--params` entry before creating anything. The real client follows pagination, sends the token, posts the workflow body CUBE expects and maps errors, against a local HTTP stub. The token appears in no output file, console line or `repr`. The parser serialises for ChRIS with no required flag, and `chris_plugin_info` describes the installed package.

Version 1.0.0 was run live on a miniChRIS with CUBE 6.11.0, pfcon 5.2.3 and pman 6.2.0. Three subject directories were uploaded and copied into a feed by pl-dircopy, whose node presents them under one link directory, and a one-piping pipeline of pl-shexec counting lines was registered. A dry run under the data node read the node's id from the job environment and wrote both records. A real run with `--itemDepth 2` created three workflows under the data node, titled `sub-01`, `sub-010` and `sub-02`; each finished successfully, and each child's job record shows it processed its own subject's file and no other, `sub-01`'s anchored filter not selecting `sub-010`. A second run skipped all three. A run with `--itemParam dirFiltr` was rejected, finished with error in ChRIS, and created nothing. The token appeared in none of the feed's files, instance records or parameters.

Version 2.0.0 was run live on the same miniChRIS against pl-freesurfer 1.0.0, built on shexec 2.3.0, under a pl-dircopy node holding two subjects, each a directory with one MGZ volume under the node's link directory, and with the pipeline `FreeSurfer 8.2.0 per subject` registered and already mapped once by 1.0.0 under the same node. A plugin run with `--plugin pl-freesurfer`, `--itemFileFilter 'glob:*.mgz'`, no depth, and `--params` setting pl-freesurfer's command to `mri_convert` for speed, found both subjects under the link directory, took the only registered version, and created two instances under the data node, titled `sub-01` and `sub-02`, each with the 32Gi minimum of its plugin; each converted its own subject's volume and no other, and their parameters show the anchored filter and the command. The instances the earlier workflows had made, of the same plugin and the same titles, were not taken as this run's. A rerun skipped both; a run naming version 9.9.9 was rejected, finished with error, and created nothing; a pipeline run with the same file filter skipped both items, finding the earlier workflows. The token appeared in none of the feed's files or the instances' parameters.

Version 2.1.0 was run live on the same miniChRIS under a pl-dircopy node holding a series-per-subject DICOM layout: `sub-01` with `MPRAGE` and `localizer` series, `sub-02` with `MPRAGE`, `MPRAGE_2` and `localizer`, each file ending `.dcm`. With `--plugin pl-freesurfer`, `--itemFileFilter 'glob:*.dcm'`, `--itemDirFilter 're:MPRAGE[^/]*$'` and `--params` setting pl-freesurfer's `fileFilter` to `glob:*.dcm` and its command to a copy of the chosen file, it created three instances titled `sub-01/MPRAGE`, `sub-02/MPRAGE` and `MPRAGE_2`, each of which copied a file of its own series and of no other, and none for the localizers. A rerun skipped all three.

Version 2.1.1 was run live on the same miniChRIS under a node of two NIfTI subjects. A plugin run whose children's command was `false` created two pl-freesurfer instances, both of which finished with error; a rerun with a command that succeeds created two new instances for the same items, and a third run skipped both, taking the successful instances as the items' children and passing over the failed ones.
